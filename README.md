# 🎯 MAC 연산 기반 2D 패턴 인식 및 검증 시뮬레이터

> 2차원 행렬 입력이 **`Cross(+)` 패턴**에 가까운지 **`X` 패턴**에 가까운지 MAC(Multiply-Accumulate) 연산으로 판별하고, 외부 JSON 데이터셋 검증 및 자동 테스트 패턴 생성·분류를 수행하는 Python CLI 기반 시뮬레이터입니다.

## 📌 1. 프로젝트 구조 및 MVC 아키텍처

본 프로젝트는 **MVC (Model-View-Controller)** 패턴을 기반으로 핵심 연산(`Service`)과 파일 입출력(`Repository`) 계층을 명확히 분리하여 설계되었습니다.

### 📁 폴더 및 파일 구조


## 🔍 3. 핵심 알고리즘 및 구조 설계

### 1) 라벨 정규화 (Label Normalization)

외부 데이터셋의 다양한 라벨 표기법(`"+"`, `"cross"`, `"CROSS"`, `"x"`, `"X"`)을 대소문자 구문 없이 표준 정규 라벨(`Cross`, `X`)로 변환합니다.

```text
"  +  "     ──►  "Cross"
"CROSS"    ──►  "Cross"
" x "      ──►  "X"
"UNKNOWN"  ──►  None (매핑 실패 원인 보관)
```

### 2) 1D 메모리 배치 최적화 (Memory-Contiguous Flattening)

파이썬 2차원 리스트는 행마다 메모리 주소가 흩어져 있어 2단계 주소 점프 탐색이 발생합니다. 반면 1차원 리스트는 연속된 메모리 주소에 데이터가 배치되므로 캐시 효율(Cache Hit Ratio)을 극대화할 수 있습니다.

```text
1. 기존 2D 리스트 구조 (행 리스트마다 메모리 주소가 흩어져 있음)
[바깥 리스트 포인터 배열: 0x1000]
  ├── [0] (0x1000) ──► 0x2400 (점프!) ──► [0x2400]: 0.1 | 0.9 | 0.1
  ├── [1] (0x1008) ──► 0x5810 (점프!) ──► [0x5810]: 0.9 | 0.9 | 0.9
  └── [2] (0x1010) ──► 0x9120 (점프!) ──► [0x9120]: 0.1 | 0.9 | 0.1
  ※ 매 원소 접근마다 [바깥 리스트 → 행 리스트 → 원소] 2단계 참조(Pointer Indirection) 및 행 전환 시 메모리 점프 발생

2. 최적화 1D 리스트 구조 (단일 포인터 배열이 연속된 번지에 정렬됨)
[1차원 리스트 포인터 배열: 0x3000]
  └──► [0x3000] 0.1 ─► [0x3008] 0.9 ─► [0x3010] 0.1 ─► [0x3018] 0.9 ─► [0x3020] 0.9 ...
  ※ 8바이트(64비트 포인터) 단위로 연속된 배열을 단일 루프로 순차 접근 (이중 인덱싱 제거 및 CPU 캐시 효율 향상)
```

### 3) 부동소수점 오차 및 동점 처리 정책 ($EPSILON = 10^{-9}$)

부동소수점 연산 특성상 발생하는 이진 오차로 인해 두 점수 차이가 $|Score_{Cross} - Score_X| < 10^{-9}$ 이하인 경우, 어느 한쪽으로 단정하지 않고 안전하게 `UNDECIDED(판정 불가)`로 격리합니다.

## 📊 4. 결과 분석 리포트

### 🔍 실패(FAIL) 케이스 3대 진단 분류 기준

테스트 검증 과정에서 실패(`FAIL`)가 발생하면, 어느 단계에서 문제가 생겼는지 즉시 파악할 수 있도록 파이프라인 순서에 따라 3가지 카테고리로 원인을 분류합니다.

| 진단 카테고리 | 세부 에러 유형 (`ErrorType`) | 발생 시점 및 판단 기준 |
| :--- | :--- | :--- |
| **1. [데이터/스키마 문제]** | 스키마 오류, 매칭 필터 없음, 크기 불일치, 비정상 수치(`NaN`/`Inf`/범위 초과), 유효하지 않은 라벨 | **연산 전 입력 검증 단계**: 데이터 형식이나 규격 자체가 잘못되어 MAC 연산을 수행할 수 없는 경우 |
| **2. [수치 비교 문제]** | 판정 불가 (`UNDECIDED`) | **점수 비교 단계**: 연산은 정상 완료되었으나 두 점수 차이가 허용오차(`1e-9`) 미만이어서 우열을 가릴 수 없는 경계값인 경우 |
| **3. [로직 문제]** | 예측 불일치 (`PREDICTION_MISMATCH`) | **최종 결과 대조 단계**: 입력 형식과 점수 차이 모두 뚜렷하여 명확한 예측값을 도출했으나, 데이터셋의 기대 라벨(`expected`)과 결과가 다른 경우 *(※ 알고리즘 오작동 또는 데이터셋 정답 라벨링 오류 시 발생)* |

### 4-2. ⚡ 성능 비교 표 및 시간 복잡도 $O(N^2)$ 분석

10회 반복 측정된 행렬 크기별 평균 연산 시간 비교 결과입니다.

| 행렬 크기 ($N \times N$) | 기존 2D 연산 (ms) | 최적화 1D 연산 (ms) | 속도 개선율 (%) | 총 연산 횟수 ($N^2$) | $3 \times 3$ 대비 연산 배율 |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **$3 \times 3$** | `0.001 ms` | `0.001 ms` | **`41.5%`** | `9 회` | $1.00 \times$ |
| **$5 \times 5$** | `0.003 ms` | `0.002 ms` | **`39.4%`** | `25 회` | $2.78 \times$ |
| **$13 \times 13$** | `0.015 ms` | `0.010 ms` | **`32.2%`** | `169 회` | $18.78 \times$ |
| **$25 \times 25$** | `0.048 ms` | `0.028 ms` | **`41.8%`** | `625 회` | $69.44 \times$ |

#### 📈 시간 복잡도 $O(N^2)$ 성립 이유

1. 한 변의 길이가 $N$인 2차원 행렬의 총 원소 개수는 $N \times N = N^2$개입니다.
2. MAC 연산 시 모든 원소 위치의 필터 값과 패턴 값을 1:1 곱하여 합산하므로, 연산 횟수는 $N$의 제곱에 정확히 비례합니다.
3. 실제로 행렬 크기가 $3 \times 3$ ($9$회 연산)에서 $25 \times 25$ ($625$회 연산)로 증가할 때 **연산 횟수는 약 69.44배** 증가하였으며, 실행 시간 역시 제곱 곡선을 따라 증가함을 실증적으로 확인하였습니다.
